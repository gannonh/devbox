# Setup

Run on `/ps setup`. Maintains the model roster that `references/delegation.md` reads, in the global instruction files every harness already loads.

There is no ps-owned config file. The roster lives in `AGENTS.md` because model routing applies to all delegated work, not only to `ps`, and because a file the harness already loads is in context without anyone reading it.

## 1. Find the canonical file

`AGENTS.md` is usually one real file that the other harnesses symlink to. Resolve them and report what you find:

```bash
for f in ~/.agents/AGENTS.md ~/.pi/agent/AGENTS.md ~/.codex/AGENTS.md ~/.claude/CLAUDE.md; do
	printf '%-28s ' "$f"
	if [ -L "$f" ]; then echo "symlink -> $(readlink "$f")"
	elif [ -f "$f" ]; then echo "real file"
	else echo "missing"; fi
done
```

The canonical file is the real one the symlinks point at. When two are real files with different contents, say so and ask which is canonical rather than guessing. When two are real files with identical contents, offer to replace the copy with a symlink so it stops drifting.

## 2. Detect available models

Never write a slug you have not confirmed. Sources, in order of reliability:

- The models the harness will accept for a subagent in this session.
- `pi --help` and the provider list in `~/.pi/agent/settings.json` when pi is installed.
- The roster already written in the canonical `AGENTS.md`.

If you cannot detect any, ask the user to paste the slugs they have access to.

## 3. Show the current mapping and confirm

Read the existing `## Sub-agents` section. Present each role from `references/delegation.md` (`explorer`, `code`, `judgment`, `panel`, `worker`) with the model it currently resolves to, marking any slug not in the detected set as needing a choice. Ask whether to accept as-is or change specific roles, using the harness's ask-user tool rather than free text.

`panel` is a list, and its length sets the fan-out. Prefer one entry per distinct provider family; the diversity is the point.

## 4. Write the managed block

Update the existing `## Sub-agents` section in place. Do not add a second roster alongside it. Wrap only the generated part in markers so re-runs replace rather than append:

```markdown
<!-- ps:models:start -->
...role lines...
<!-- ps:models:end -->
```

Rewrite everything between the markers, leaving the rest of the file untouched. Absent markers, insert them inside `## Sub-agents`, preserving the prose already there.

Show the diff and get confirmation before writing. These are global files that affect every session in every harness.

## 5. Propagate

- Canonical `AGENTS.md`: written in step 4.
- Any harness whose file symlinks to canonical: nothing to do. Say so.
- A harness whose file is a real copy: offer to replace it with a symlink to canonical. On no, write the same block there too and note that it will drift.
- Cursor reads `~/.cursor/rules/*.mdc` globally rather than a home-level `AGENTS.md`. Write `~/.cursor/rules/ps-models.mdc` with `alwaysApply: true` frontmatter and the same role lines. Overwrite the whole file so re-runs stay idempotent ([Make Operations Idempotent](references/principles/make-operations-idempotent.md)).

## 6. Confirm

Report which files changed, which were already symlinks, and that the roster applies to new sessions. Re-running updates it.

## 7. Offer a verification skill

Check whether the project has a scripted way to drive the real app for proof (a `verify-*` skill, or an existing harness). If not, offer once: a project-local verification skill lets agents drive the app the way a user does and prove changes work, generated by `references/verification/create.md`. On no, move on without pushing.
